# Migration `v1.2.2`

Invoked automatically by `/update-vault` **step 6** (after **step 5** has propagated the changed template files), for any vault in version < 1.2.2.

- **Part A — per-type frontmatter validation (#104)**: heads-up + triage for the stricter `validate-wiki.py`. Read-only checks and a guided, interactive backfill — **never blocks the verdict**.

## Part A — per-type frontmatter validation (#104)

### A0. Context

`.claude/rules/frontmatter.md` has always declared per-type mandatory fields, but nothing enforced them: a `type: decision` page without `status`, or a `type: source` page carrying `source_sha256: TODO`, passed CI green. `validate-wiki.py` now checks, per page type:

- `type: decision` → `status` present, in the closed enum `pending | accepted`; a non-null `verdict` must be in `validated | invalidated | partial` and be accompanied by `verdict_date` and `verdict_evidence`;
- `type: source` → `source_path`, `source_sha256` (64-char lowercase hex — placeholders are rejected) and `ingested` present.

Unknown types (`index`, `log`, `radar`…) have no per-type requirements and are unaffected.

### A1. Triage (read-only)

Run the validator in its transitional warn-only mode — it reports the new per-type defects as `WARN:` lines on stderr without failing:

```bash
python3 scripts/wiki-maint/validate-wiki.py --warn-frontmatter-types 2>&1 >/dev/null | grep WARN || echo "clean"
```

If it prints `clean`: nothing to do, this Part is done — the vault already satisfies the schema.

### A2. Backfill (interactive)

For each warned page, propose the fix through `AskUserQuestion` (never edit silently):

- **`status` missing on a decision** — read the page body; propose `accepted` when the ADR was applied, `pending` otherwise. Values outside the enum (`validated`, `approved-implemented`, …) map to `accepted` when the decision was adopted; the reality-check dimension belongs in `verdict`, not `status`.
- **`verdict` set without `verdict_date`/`verdict_evidence`** — either fill the companions from the page body (date + one-line narrative) or reset `verdict: null` until reality validates.
- **`source_sha256` missing or placeholder** — recompute from the raw file when it exists: `shasum -a 256 <source_path> | awk '{print $1}'`. If the raw file is gone, flag the page to the user (orphan concern, see `scan-raw.sh --orphans`) instead of inventing a hash.
- **`ingested` missing** — use the page's `created` date as the best available approximation, and say so.

### A3. Verify

```bash
python3 scripts/wiki-maint/validate-wiki.py
```

Expected: `✓ wiki integrity: clean`. Until the backfill is complete, the vault's CI (`lint.yml` → `wiki-integrity`) will fail on these defects — that is the intended enforcement; `--warn-frontmatter-types` exists precisely to stage the transition locally.

## Idempotence

- **Re-run A1** on a vault whose pages already satisfy the schema → prints `clean` (no warnings).
- **Re-run A2** after a backfill is complete → re-proposes only pages that still warn (none, if complete); a second run is a no-op.
- Partial backfills are safe to resume: the validator tags only pages that still fail; re-running the migration picks up the next batch.

- K pages with verdict set but missing companions (backfilled from body or reset to null)

(Counts are from the backfill interactive steps.)

## Commit

Only if **A2 changed any pages** (i.e., at least one `AskUserQuestion` → Applied):

```bash
git add wiki/
git commit -m "chore: migrate to v1.2.2 (frontmatter backfill)"
```

If no pages were changed (vault already clean, or user skipped all proposals), skip this commit.

## Verdict for `/update-vault`

Part A yields **Applied** regardless of backfill completion. Here is the rationale:

The per-type frontmatter defects are **pre-existing vault data**, not a template transformation; `/update-vault` step 5 has already delivered the stricter `validate-wiki.py` via file propagation. The migration's job is to surface them and offer an interactive backfill path. An incomplete backfill (some pages still warn) is a **data quality discovery, not a migration failure** — like Part C in v1.2.0 (see v1.2.0.md ~L412), which reports newly-detected defects without blocking.

Therefore:

- If the user **completes** the backfill (all pages pass validation) → verdict is **Applied** (migration succeeded, vault is ready).
- If the user **skips** the backfill (leaves pages unchanged) → verdict is still **Applied** (migration succeeded, vault is aware; CI will enforce the schema, giving the user a chance to fix it incrementally).
- If the user **partially completes** the backfill → verdict is **Applied** (migration succeeded, remaining defects are noted in the log).

In all cases, **`/update-vault` may bump `.claude/template-version` to 1.2.2** — the migration code shipped; the backfill is the vault's own concern.
