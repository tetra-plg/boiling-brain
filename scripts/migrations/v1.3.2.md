- **Part B — daily schedule (#154)**: optional, interactive install of the local schedule — **never blocks the verdict**.

## Part A — batch ingestion of the pending queue (#154)

### A0. Context

Drops made through `drop_to_raw` / `drop_file_to_raw` queue up in `cache/.pending-ingest`, but nothing consumed that queue except an operator typing `/ingest`, and a second `ingest_start` while a job ran was refused with an error. This release adds:

- **`scripts/ops/ingest-pending.py`** (+ `test_ingest_pending.py`, `fixtures/last-batch.example.json`) — new. Ingests the queue sequentially, one guarded headless run per entry (the same command as `ingest_start`), per-file status `ok` / `degraded` / `failed` / `skipped-no-hint`, writes `ops/ingest/last-batch.json` and, when the vault keeps a run ledger (`ops/metrics/ledger.config.json`), one run event to `ops/metrics/runs.jsonl`.
- **`scripts/ops/schedule-ingest.sh`** (+ `test_schedule_ingest.py`) — new. Installs, reports or removes a daily local schedule of the runner (see Part B).
- **`scripts/mcp/mcp-wiki.py`, `scripts/mcp/ingest_jobs.py`** — new MCP tool `ingest_pending(domain_hint="", max_files=0)` (19 tools); `ingest_start` / `ingest_pending` started while a job runs are **queued** (FIFO) instead of refused; `ingest_status` says `queued (position N)`; `ingest_cancel` drops a queued job. `cache/ingest.lock` keeps the MCP jobs and the scheduled batch from running two headless ingests at once. `drop_to_raw` / `drop_file_to_raw` accept an optional `domain_hint`.
- **`cache/.pending-ingest` format** — an entry may now be `<path><TAB><domain-hint>`; a line without TAB is a plain path, as before. `scan-raw.sh --pending` and `purge-pending-ingest.sh` read both forms. A vault-local script that reads the manifest line by line must split on the TAB (`cut -f1`) — check with `grep -rn "pending-ingest" scripts/ .claude/ --include=*.sh --include=*.py`, ignoring the template's own files.
- **`.claude/commands/ingest.md`** — `--pending` flag (`--pending --headless` runs the batch runner). **`scripts/mcp/setup-mcp.sh`** — the global `~/.claude/CLAUDE.md` block mentions `ingest_pending` and queueing; its freshness probe moved to `ingest_pending`. **`.gitignore`** — `ops/ingest/` (run outputs, never committed).

All of these are template files: step 5 propagated them (new files are pre-checked in its selection). Check that the new scripts landed and that the outcome directory is ignored:

```bash
test -f scripts/ops/ingest-pending.py && test -f scripts/ops/schedule-ingest.sh && echo "present" || echo "absent"
git check-ignore -q ops/ingest/last-batch.json && echo "ignored" || echo "not ignored"
```

If `absent`: the files were deselected at step 5 — re-run `/update-vault` and keep them selected; `ingest_pending` depends on them. If `not ignored` (the vault keeps its own `.gitignore`): propose via `AskUserQuestion` appending the line `ops/ingest/` to `.gitignore`.

### A1. MCP reload heads-up

The new tool and the queueing live in the MCP server process. Until it restarts, the server keeps the previous tool list and still refuses a second job. **Step 7** of `/update-vault` already offers `setup-mcp.sh` (it refreshes the `~/.claude/CLAUDE.md` block) and the reload — no extra action here. Claude Desktop / Cowork: quit and reopen the app.

### A2. Optional `CLAUDE.md` patch (interactive)

The vault's `CLAUDE.md` is user-owned. Its "Session start" bullet on `cache/.pending-ingest` predates the hint column. Propose via `AskUserQuestion` (never edit silently) replacing that bullet with:

```markdown
- **`cache/.pending-ingest`**: paths awaiting ingestion, one per line, optionally followed by a TAB and a domain hint. Run `bash scripts/scan-raw.sh` first — purge silently the `SKIP` (stale, already ingested), suggest `/ingest <path>` for `NEW` / `MODIFIED` entries (or `/ingest --pending --headless` for the whole queue). Remove the file if empty.
```

Skip if the bullet already mentions the TAB, or if the vault has no such bullet. A decline is harmless: the hint is metadata for the batch runner.

`docs/cowork-project-instructions.md` §4 now mentions queueing and the drop-time `domain_hint`. A copy pasted into a Claude Desktop / Cowork project is out of file propagation's reach: tell the user they may re-paste §4. Nothing to run.

## Part B — daily schedule (#154)

### B0. Context

`scripts/ops/schedule-ingest.sh install --at HH:MM` runs the batch every day on this machine, with the operator's own Claude Code login: a user LaunchAgent on macOS (a run missed while asleep starts at wake), a systemd user timer with `Persistent=true` on Linux (or a tagged crontab line without a systemd user instance). Output goes to `ops/ingest/scheduled.log`, the outcome to `ops/ingest/last-batch.json`. Windows is not supported yet.

### B1. Offer (interactive, optional)

Ask via `AskUserQuestion` whether to install a daily schedule. Only vaults fed continuously (drops from an agent or a capture tool) benefit; a vault ingested by hand does not need it. On yes, ask for the time (`HH:MM`), an optional fallback domain slug (`list_domains`) and whether unattended runs may use a permission mode (recommended `auto`, the same deliberate opt-in as `MCP_INGEST_PERMISSION_MODE`), then run:

```bash
bash scripts/ops/schedule-ingest.sh install --at <HH:MM> [--domain-hint <slug>] [--permission-mode <mode>]
bash scripts/ops/schedule-ingest.sh status
```

A decline is fine: the same command can be run at any time, and `ingest_pending()` / `/ingest --pending --headless` work without a schedule.

### Verdict for `/update-vault`

Part B is **Applied** whatever the answer: the schedule is a machine-local choice, not a vault transformation.

## Idempotence

- **A0** is read-only; its `.gitignore` line and **A2** are exact-string-guarded edits — safe to re-run.
- **B1**: `install` replaces an existing schedule of the same vault (same label / unit name), never duplicates it; `uninstall` removes every file `install` created.
