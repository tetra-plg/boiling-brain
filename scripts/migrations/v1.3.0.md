# Migration `v1.3.0`

Invoked automatically by `/update-vault` **step 6** (after **step 5** has propagated the changed template files), for any vault in version < 1.3.0.

- **Part A — per-type frontmatter validation (#104)**: heads-up + triage for the stricter `validate-wiki.py`. Read-only checks and a guided, interactive backfill — **never blocks the verdict**.
- **Part B — CLAUDE.md SYNC-REPOS block up to date (#106)**: the vault's `CLAUDE.md` is user-owned and never propagated by step 5, so its `SYNC-REPOS` block (injected verbatim from `BOOTSTRAP.md` at bootstrap) keeps the pre-#106 skip-if-exists wording forever unless offered an update here. Interactive, doc-only — **never blocks the verdict**.
- **Part C — format parity & MCP reload (#112, #124)**: heads-up on the machine-level prerequisites and the MCP server reload needed for two additions shipped together in this release — pandoc for `.docx`/`.pptx`, an MCP server reload for `drop_file_to_raw`, and the same reload for the new async ingestion tools (`ingest_start`/`ingest_status`/`ingest_cancel`). ## Part A — per-type frontmatter validation (#104)

### A0. Context

`.claude/rules/frontmatter.md` has always declared per-type mandatory fields, but nothing enforced them: a `type: decision` page without `status`, or a `type: source` page carrying `source_sha256: TODO`, passed CI green. `validate-wiki.py` now checks, per page type:

- `type: decision` → `status` present, in the closed enum `pending | accepted`; a non-null `verdict` must be in `validated | invalidated | partial` and be accompanied by `verdict_date` and `verdict_evidence`;
- `type: source` → `source_path`, `source_sha256` (64-char lowercase hex — placeholders are rejected) and `ingested` present.

Unknown types (`index`, `log`, `radar`…) have no per-type requirements and are unaffected.

### A1. Triage (read-only)

Run the validator in its transitional warn-only mode — it reports the new per-type defects as `WARN:` lines on stderr without failing:

```bash
python3 scripts/wiki-maint/validate-wiki.py --warn-frontmatter-types 2>&1 >/dev/null | grep WARN || echo "clean"
```

If it prints `clean`: nothing to do, this Part is done — the vault already satisfies the schema.

### A2. Backfill (interactive)

For each warned page, propose the fix through `AskUserQuestion` (never edit silently):

- **`status` missing on a decision** — read the page body; propose `accepted` when the ADR was applied, `pending` otherwise. Values outside the enum (`validated`, `approved-implemented`, …) map to `accepted` when the decision was adopted; the reality-check dimension belongs in `verdict`, not `status`.
- **`verdict` set without `verdict_date`/`verdict_evidence`** — either fill the companions from the page body (date + one-line narrative) or reset `verdict: null` until reality validates.
- **`source_sha256` missing or placeholder** — recompute from the raw file when it exists: `shasum -a 256 <source_path> | awk '{print $1}'`. If the raw file is gone, flag the page to the user (orphan concern, see `scan-raw.sh --orphans`) instead of inventing a hash.
- **`ingested` missing** — use the page's `created` date as the best available approximation, and say so.

### A3. Verify

```bash
python3 scripts/wiki-maint/validate-wiki.py
```

Expected: `✓ wiki integrity: clean`. Until the backfill is complete, the vault's CI (`lint.yml` → `wiki-integrity`) will fail on these defects — that is the intended enforcement; `--warn-frontmatter-types` exists precisely to stage the transition locally.

## Part B — CLAUDE.md SYNC-REPOS block up to date (#106)

### B0. Context

`/sync-repos` used to skip re-syncing a source whenever `<dest>/<shortsha>/` already existed, full stop — editing the manifest's `paths`/`exclude_paths` had no effect until an unrelated upstream commit moved the SHA. #106 made the SKIPPED guard perimeter-aware: on an existing `<shortsha>` dir, the script now compares the manifest's current perimeter against the latest revision's `.sync-meta.json` and, on any difference, captures a **perimeter revision** `<shortsha>-rN` beside it.

`scripts/sync-repos.sh` and the propagated `.claude/commands/sync-repos.md` / `docs/tracked-repos-immutable-snapshots.md` already reflect this (delivered by step 5 file propagation). The `### SYNC-REPOS` block inside the vault's **`CLAUDE.md`**, however, was injected **verbatim** at bootstrap from `BOOTSTRAP.md` Annex D and is **user-owned** — step 5 never touches it. Any vault bootstrapped before #106 therefore keeps the stale "if that folder already exists → skip" wording forever unless offered an update here.

### B1. Locate the SYNC-REPOS block

Search the vault's `CLAUDE.md` for the `### SYNC-REPOS` heading (or its localized equivalent, if the vault's `CLAUDE.md` was translated — identify it by role: the block documenting the `/sync-repos` manifest, target resolution and mechanics). If `has_tracked_repos` was `false` at bootstrap, the block may be absent entirely — skip B2, nothing to do.

### B2. Propose the wording update (interactive)

Within the located block, look for the two stale sentences (or their localized equivalent):

- **SHA-keyed snapshot principle** — `"If that folder already exists → skip. A merge into main upstream = a new SHA = a new snapshot beside the old."`
- **Mechanics step 2** — `"If <dest>/<shortsha>/ exists → SKIPPED."`

If both already carry the perimeter-revision mention (idempotence check — look for `#106` or `perimeter revision` near either sentence): nothing to do, this Part is done.

Otherwise, propose via `AskUserQuestion` (never edit silently) replacing them with the current wording from `BOOTSTRAP.md` Annex D (`### D. SYNC-REPOS block to inject into CLAUDE.md`):

- **SHA-keyed snapshot principle** → `"If that folder already exists → skip, unless the manifest's paths/exclude_paths changed for that SHA, in which case a perimeter revision <shortsha>-rN is created beside it (#106). A merge into main upstream = a new SHA = a new snapshot beside the old."`
- **Mechanics step 2** → `"If <dest>/<shortsha>/ exists → SKIPPED, unless paths/exclude_paths changed for that SHA, in which case a <shortsha>-rN revision is created (#106)."`

If the vault's block was heavily customized (rewritten prose, removed sentences) such that the stale lines can't be confidently matched: show the block and let the user place the update, or decline. A decline is a valid outcome — see Verdict below.

### B3. Idempotence & user customizations

Re-running Part B is safe: B2's idempotence check skips a block that already mentions the perimeter-revision case. Never overwrite user edits — a decline is re-proposed at the next `/update-vault` (per the migration contract), and the migration verdict is unaffected either way (see Verdict below).

## Idempotence

- **Re-run A1** on a vault whose pages already satisfy the schema → prints `clean` (no warnings).
- **Re-run A2** after a backfill is complete → re-proposes only pages that still warn (none, if complete); a second run is a no-op.
- Partial backfills are safe to resume: the validator tags only pages that still fail; re-running the migration picks up the next batch.
- **Part B**: re-running is a no-op once the block mentions the perimeter-revision case (B2's idempotence check); a decline is safely re-proposed by the next `/update-vault`.

## Verdict for `/update-vault`

Parts A and B both yield **Applied** regardless of backfill/update completion (Part C carries its own verdict, below — also always Applied). Here is the rationale:

The per-type frontmatter defects are **pre-existing vault data**, not a template transformation; `/update-vault` step 5 has already delivered the stricter `validate-wiki.py` via file propagation. The migration's job is to surface them and offer an interactive backfill path. An incomplete backfill (some pages still warn) is a **data quality discovery, not a migration failure** — like Part C in v1.2.0 (see v1.2.0.md ~L412), which reports newly-detected defects without blocking.

Similarly, the stale `CLAUDE.md` wording is a **user-owned file**, never propagated by step 5; Part B's job is to surface the staleness and offer an update, not to enforce it. A decline leaves the vault's docs slightly imprecise but does not affect the script's actual (already-correct) behavior — a **doc discovery, not a migration failure**.

Therefore:

- If the user **completes** the backfill (all pages pass validation) → Part A is **Applied** (migration succeeded, vault is ready).
- If the user **skips** the backfill (leaves pages unchanged) → Part A is still **Applied** (migration succeeded, vault is aware; CI will enforce the schema, giving the user a chance to fix it incrementally).
- If the user **partially completes** the backfill → Part A is **Applied** (migration succeeded, remaining defects are noted in the log).
- Whether the user **accepts or declines** the Part B `CLAUDE.md` update → Part B is **Applied** either way (doc-only, user-owned file — see B0/B3; a decline is re-proposed at the next `/update-vault`).

In all cases, **`/update-vault` may bump `.claude/template-version` to 1.3.0** — the migration code shipped; the backfill and the `CLAUDE.md` wording update are each the vault's own concern.

## Part C — format parity & MCP reload: pandoc prerequisite + async ingestion tools (#112, #124)

### C0. Context

`/update-vault` step 5 has already propagated the code: the MCP server exposes a new `drop_file_to_raw(source_path, subfolder)` tool (server-side copy of a local binary into `raw/`), `/ingest` now converts `.docx`/`.pptx` into a markdown twin through the new `scripts/convert-doc.sh`, and the server also gains three async ingestion tools (`ingest_start`/`ingest_status`/`ingest_cancel`, #124, see C3). Two things the file propagation cannot deliver by itself:

1. **pandoc** — a machine-level binary, not a vault file. Without it, `.docx`/`.pptx` ingestion fails with an actionable message; everything else keeps working.
2. **A running MCP server still on the previous code** — re-registration does not reload the live process, so neither `drop_file_to_raw` nor the three async tools become visible until it does.

This Part is a heads-up on both. Read-only: it never edits a vault file.

### C1. pandoc check (read-only)

```bash
command -v pandoc >/dev/null 2>&1 && pandoc --version | awk 'NR==1 {print "pandoc", $2}' || echo "absent"
```

- **Absent** → tell the user, with the install command for their platform (macOS: `brew install pandoc`; Debian/Ubuntu: `apt install pandoc`; otherwise <https://pandoc.org/installing.html>). Not blocking: the vault works exactly as before, only `.docx`/`.pptx` ingestion is unavailable, and `scripts/convert-doc.sh` exits `2` with that same message when reached.
- **Present, major version < 3** → `.docx` conversion works; **`.pptx` input needs pandoc ≥ 3.0**. Mention the upgrade, don't insist.
- **Present, major version ≥ 3** → nothing to do.

Do not install anything on the user's behalf.

### C2. MCP reload heads-up

If step 5 propagated `scripts/mcp/mcp-wiki.py` (it did, if the user kept the file in the selection), **step 7** of `/update-vault` already offers `setup-mcp.sh` and prints the reload instruction. Add one precision here: `drop_file_to_raw` only becomes visible to MCP clients — Claude Code, Claude Desktop, Claude Cowork — **after the server process is restarted**, which for Claude Code means restarting the session, and for the desktop apps means quitting and reopening them.

Since #133, `setup-mcp.sh` also writes the Desktop/Cowork side itself: it merges the server entry into `claude_desktop_config.json` (macOS `~/Library/Application Support/Claude/`, Windows `%APPDATA%\Claude\`, Linux `~/.config/Claude/`) whenever that directory exists, and prints a clear skip notice when the app is not installed. Vaults that ran an earlier setup-mcp.sh and never saw the connector in Desktop/Cowork: re-run `bash scripts/mcp/setup-mcp.sh` (or accept the step 7 offer), then restart the app.

Also worth stating once: the tool reads from the vault owner's `$HOME` by default. A vault whose sources live outside `$HOME` (external drive, network share) must set `LLMWIKI_DROP_SOURCE_ROOTS` (an `os.pathsep`-separated list of directories) in the environment the MCP server is registered with.

### C3. Async ingestion tools reload (#124)

The same reload constraint from C2 applies to a second addition delivered alongside format parity in this release: the MCP server gains three async ingestion tools (`ingest_start`/`ingest_status`/`ingest_cancel`, surface 15 → 18, #124). After propagation, re-run `bash scripts/mcp/setup-mcp.sh` (or accept the `/update-vault` step 7 offer): it refreshes the global `CLAUDE.md` block — whose freshness probe now looks for `ingest_start` instead of `drop_file_to_raw` — and reload the running MCP server (restart your Claude session or `claude mcp remove`/`claude mcp add`) so the new tools are actually exposed. Heads-up only, never blocking: the sync `ingest()` keeps working unchanged either way.

### Verdict for `/update-vault`

Part C is **Applied** in all cases: it reports machine-level prerequisites, it does not transform the vault. A missing pandoc is a capability the user may or may not want; a not-yet-reloaded MCP server is a transient state the user resolves on their own schedule — neither blocks the version bump.
